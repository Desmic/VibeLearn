# Future game-research agent stage

Status: planned boundary, 20 September 2026. No dispatcher or live provider added.
User direction: conduct deeper research now across ten games; later make this a
separate agent stage in the general system. Initial reference output:
`GAME-REFERENCE-STUDY.md`. Terminal PM remains the future orchestration owner under
`AUTOMATED-DEVELOPMENT-SYSTEM.md`; its live-run policy is unchanged.

## Purpose and handoff

`experience brief -> bounded research -> creative direction -> playable chunk ->
cold native review -> intent comparison -> repair and recheck`

The researcher supplies options and evidence. Astra owns creative synthesis and
art/world direction. Research does not certify our game or replace the fresh-context
Astra reviewer across existing critic lanes. The cold reviewer receives the player
surface and task constraints before any research rationale or creator explanation.

## Input contract, initially human-readable

- Audience, learning outcomes, intended feelings, session length, device/control
  constraints, current experience boundary and production limits.
- Explicit questions: for example attachment before a mission, readable spatial
  choice, useful knowledge, or rewarding recovery. Avoid an unbounded request to
  make a game great.
- User-named references, selection cap (ten for this initial study), evidence/time
  budget and exclusions. Motion/audio quality are currently deferred.
- Known native-play failures and areas where new research could change a decision.
  Keep this input separate from the later cold-review packet.

## Research procedure

1. Select for question coverage and diversity. Record Metacritic platform, edition,
   critic score, source and access date; identify award body/year for award claims.
   Permit a lower-score reference with a specific reason. Do not optimize the list
   by selecting whichever small-sample port has the highest score.
2. Prefer developer talks, interviews, actual gameplay demonstrations and in-game
   commentary. Read the substantive source, including relevant transcripts.
   Search snippets and marketing adjectives do not constitute a study.
3. Record exact evidence scope: full or partial transcript with time range,
   authored/automatic captions and language, selected visual frames, active play,
   or unavailable. Separate prerelease demonstrations from shipped-game evidence.
   Use an accessible alternate source when needed and retain the limitation.
4. Extract a concrete example and mechanism. Distinguish what was observed, what
   the developer says they intended, and what the researcher infers. Keep URLs and
   timestamps/section locators. Store original summaries, not copied transcripts.
5. Challenge transfer: audience mismatch, conflicting reference, implementation
   cost, accessibility, device limitations, content suitability and failure modes.
   A popular mechanic is not automatically a useful learning mechanic.
6. Produce a bounded adaptation with an observable test. At least one decision
   addresses art/world direction. Preserve original IP and learning standards.
7. Stop when the requested questions have useful, sourced options and acknowledged
   gaps. More source count is not automatically more depth. Return unresolved
   questions if an important decision still lacks evidence.

## Output record per proposed technique

| Field | Required content |
| --- | --- |
| Question | What design uncertainty this resolves |
| Reference | Game, edition/build when known, source author and provenance |
| Evidence | URL, date accessed, locator, modality, coverage and limitations |
| Observation | Concrete example without invented player feelings |
| Interpretation | Proposed mechanism and confidence; separate from observation |
| Fit | Audience, learning and production conditions where it applies |
| Countercase | When it fails or when another reference suggests the opposite |
| Adaptation | Small original design decision, not a copied setting or asset |
| Cost | Dependencies and likely implementation/review burden |
| Verification | Player action, expected observable result, failure signal, critic lane |
| Disposition | Adopt for prototype, defer, reject, or evidence still needed |

This document is the proposed contract. Introduce a machine schema only when the
actual dispatch/ingestion boundary needs it; do not build a speculative research
framework or add ten model calls merely because there are ten references.

## Acceptance and enforcement boundaries

Research is complete for its bounded question when its sources were actually
examined, important claims are locatable, disagreements are retained, and the
creative owner can choose a testable design direction. An unavailable transcript
must not become a claim to have watched the video. Developer intent is not
independent confirmation. Scores and awards justify selection, never causality.

Authoring records the chosen technique and explicit exclusions. Existing critics
then test the implemented player experience, using native GUI play with supporting
screenshots/recordings and evidence appropriate to each claim. Existing art/world
dimensions remain independent; attractive reference imagery cannot pass them.
Learning checks preserve outcomes and immutable evidence independently of theme.

For future automation, audit factual source support, decision usefulness, cost,
and whether later playtests confirmed or overturned the hypothesis. Maintain a
small collection of accepted and rejected techniques with context, not a universal
recipe. Revisit a source when an active design question or changed reference
warrants it; avoid rereading everything on every generation.

For now this stage uses the current Codex research workflow. No model cost/quality
comparison is implied, no paid API dispatch is authorized, and no additional
agent was created for this research. Terminal PM integration remains planned.
